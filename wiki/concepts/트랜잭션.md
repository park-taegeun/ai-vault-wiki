## 한 줄 정의
DB 상태를 바꾸는 작업을 "전부 되거나 전부 안 되거나"로 묶은 논리적 단위다. COMMIT으로 확정하고, ROLLBACK으로 취소하고, SAVEPOINT로 중간 취소점을 둔다.

## 핵심 내용
### ACID
| 성질 | 뜻 | 예 |
|---|---|---|
| 원자성 (Atomicity) | 전부 반영되거나 전부 취소 | 송금 = 출금 + 입금. 하나라도 실패하면 ROLLBACK |
| 일관성 (Consistency) | 실행 전후로 규칙·제약조건이 깨지지 않음 | |
| 고립성 (Isolation) | 동시에 도는 트랜잭션끼리 간섭하지 않음 | 변경 중인 데이터를 다른 트랜잭션이 건드리지 못하게 격리 |
| 지속성 (Durability) | COMMIT된 결과는 장애가 나도 남음 | 로그를 남긴 뒤 커밋하므로 커밋된 최신 데이터는 유지 |

암기는 "원일고지". (원본 노트에는 고립성이 "고유성", 지속성이 "Duration"으로 적혀 있었음 (정정))

### TCL과 실행 흐름
| 명령 | 하는 일 |
|---|---|
| `COMMIT` | 변경을 확정해 영구 반영. 커밋 전 변경은 다른 세션에 보이지 않는다 |
| `ROLLBACK` | 마지막 커밋 시점으로 되돌림. 그 뒤의 변경이 전부 취소된다 |
| `SAVEPOINT 이름` | 중간 저장점. `ROLLBACK TO 이름`이면 그 지점까지만 되돌린다 |

```sql
UPDATE acct SET bal = bal - 100 WHERE id = 1;
SAVEPOINT sp1;
UPDATE acct SET bal = bal + 100 WHERE id = 2;
ROLLBACK TO sp1;   -- 두 번째 UPDATE만 취소
COMMIT;
```

- ROLLBACK은 커밋 전에만 통한다. 커밋한 내용을 바꾸려면 새 트랜잭션으로 고친다.
- UPDATE 후 커밋·롤백 없이 오래 두면 잠금이 걸린 채로 남아 다른 사용자가 그 행을 못 바꾼다. Oracle 기준으로 다른 세션은 변경 전 값을 읽을 수는 있다.

### 무엇이 롤백되나
- **DML(INSERT·UPDATE·DELETE·MERGE)** 은 커밋 전까지 롤백할 수 있다.
- **DDL(CREATE·ALTER·DROP·RENAME·TRUNCATE)** 은 Oracle에서 실행 즉시 암묵적으로 커밋된다. 그래서 DDL 앞에 있던 미커밋 DML도 함께 확정된다.
- 다만 PostgreSQL처럼 DDL도 트랜잭션 안에서 롤백되는 DBMS가 있다. "DDL은 무조건 롤백 불가"는 DBMS마다 다르다 → [[sql]]
- 전체 삭제: 지울 마음이 확고하면 TRUNCATE가 부하 면에서 유리하다(행 단위 로그를 안 쌓음). 되돌릴 여지가 필요하면 DELETE를 쓴다.

### 회복: Undo와 Redo
- Undo = 끝나지 않은 트랜잭션의 변경을 취소, Redo = 커밋된 트랜잭션의 변경을 다시 반영
- 체크포인트는 회복을 시작할 지점이다.

| 기법 | DB 반영 시점 | 장애 시 필요한 것 |
|---|---|---|
| 즉시 갱신 | 커밋 전에도 반영 | Undo + Redo |
| 지연 갱신 | 커밋할 때까지 로그에만 | Redo만 |

지연 갱신에 Undo가 없는 이유: 커밋 전까지 DB에 쓴 게 없으니 되돌릴 것도 없다.

### 격리 수준과 이상 현상
- **Dirty Read**: 커밋 안 된 값을 읽음
- **Non-Repeatable Read**: 같은 행을 다시 읽었더니 값이 바뀜(다른 트랜잭션의 수정)
- **Phantom Read**: 같은 조건으로 다시 읽었더니 행 개수가 바뀜(다른 트랜잭션의 삽입)

| 격리 수준 | Dirty | Non-Repeatable | Phantom |
|---|---|---|---|
| READ UNCOMMITTED | 발생 | 발생 | 발생 |
| READ COMMITTED | 방지 | 발생 | 발생 |
| REPEATABLE READ | 방지 | 방지 | 발생 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

낮을수록 동시성·성능이 오르고 이상 현상이 늘어난다. 아래로 한 칸 내려갈 때마다 왼쪽부터 하나씩 막힌다.

### 병행 제어
- **잠금(Locking)**: 연산을 마칠 때까지 다른 트랜잭션의 접근을 막는다. 잠금 단위가 크면 관리가 쉽고 오버헤드가 낮지만 병행성이 떨어지고, 작으면 그 반대다. 교착상태(Deadlock)가 생길 수 있다.
- **2단계 잠금(2PL)**: 확장 단계엔 획득만, 축소 단계엔 해제만. 직렬 가능성은 보장하지만 교착상태는 못 막는다. 해제 시점만 통제하고 획득 순서는 통제하지 않기 때문이다.
- **타임스탬프**: 고유 시각으로 실행 순서를 정한다.
- **MVCC**: 여러 버전을 유지해 읽기와 쓰기가 서로 막지 않게 한다. 쓰기끼리는 여전히 충돌한다.

### 다른 맥락에서 본 트랜잭션
- 모델링: 하나의 커밋 단위로 묶어야 하는 작업은 데이터 모델에 표현할 수 있다. 주문 내역 같은 행위 엔터티는 트랜잭션마다 행이 쌓인다. 반정규화 판단 때 용량과 트랜잭션 유형부터 본다.
- 보안: 클락-윌슨 모델은 사용자가 데이터에 직접 손대지 못하게 하고, 검증된 트랜잭션을 거쳐서만 바꾸게 해 무결성을 지킨다.
- 성능 지표: 처리량(단위 시간당 트랜잭션 수), 응답 시간(입력을 마친 뒤 첫 응답까지), 경과 시간(입력부터 출력 완료까지).

## 언제 쓰나 (상황 예시)
- 계좌 이체, 주문 + 재고 차감처럼 둘 중 하나만 반영되면 데이터가 어긋나는 작업.
- 여러 단계 일괄 처리 중 뒷단계만 다시 하고 싶을 때 → SAVEPOINT.
- 대량 삭제 전: 되돌릴 가능성이 있으면 DELETE.

## 실습에서 배운 것 / 트러블슈팅
- "DDL은 자동 커밋"을 놓치면 ROLLBACK이 듣는다고 착각한다. 노트의 오답 대부분이 이 지점이었다. 반대로 이 규칙을 모든 DBMS에 일반화해도 틀린다.
- Non-Repeatable(수정)과 Phantom(삽입)은 "값이 바뀌나, 개수가 바뀌나"로 구분하면 헷갈리지 않는다.
- 같은 요청이 두 번 반영되지 않게 막는 건 DB 트랜잭션보다 한 층 위의 문제였다. 졸업작품에서는 요청 번호로 막았다 → [[idempotency-key]]
