## 한 줄 정의
같은 결정·수치의 정본을 한 곳에만 두고, 나머지는 그 정본을 참조하거나 정본과 대조만 하게 하는 원칙(SSoT)이다. 충돌하면 정본이 이긴다.

## 핵심 내용
- **띵동의 우선순위 (2026-05-07)**: 혼자 4개 도메인(firmware / ML / server / dashboard)을 22주 동안 병렬로 돌리면서, 채팅방을 새로 열 때마다 "어디까지 했더라?"를 반복하는 문제가 생겼다. 그래서 순서를 정했다.
  1. GitHub repo의 `docs/decisions.md` / `decisions-log.md`: 최상위 기준
  2. 의사결정 채팅방: 도메인별로 분리
  3. 위임 프롬프트 생성 채팅방: 코드를 직접 쓰지 않고 위임 프롬프트만 출력
  4. Claude Code(MCP): 실제 작업
  5. 노션 PoC 트래킹: 사람이 보는 화면, 기준 아님
  - 충돌 시 `decisions.md` > 프로젝트 지침 > 노션. 노션에서는 결정하지 않는다.
- **작업 체인**: 의사결정 채팅방 → 위임 프롬프트 → Claude Code가 skill + MCP로 실행 → repo와 노션에 반영. 사람은 결과 검증과 의사결정만 맡는다 → [[ai-산출물-검증]], [[nested-agent]]
- **채팅방 분리와 인계 패키지**
  - 분리 신호: 작업 덩어리 종료, 컨텍스트가 무거워질 때(응답 지연, 이전 결정 혼동, 같은 질문 반복), 큰 결정 직후.
  - 인계 패키지 순서: SSoT 링크 → 직전 완료 5~7개 → 진행 중·미결 3~5개 → 다음 첫 액션 1~3개 → 보류 사항 → 작업 원칙.
- **매일 밤 종료 루틴**: `decisions.md` 갱신 → `decisions-log.md` entry 추가 → 노션 트래킹 갱신. 1차 commit으로 log entry를 추가하고, 2차 commit으로 그 entry에 자기 commit hash를 보강하는 2-step 커밋을 쓴다.
- **옛 기록은 지우지 않고 옆에 덧붙인다**: 과거 계획 수치와 최근 실측 수치를 나란히 남긴다. 어떤 계획이 실측으로 어떻게 바뀌었는지 둘 다 보존하려는 원칙이다.
- **라이브 코드가 정본일 때도 있다**: 백엔드 응답 JSON은 추측으로 깎지 않고 프론트 타입 파일(`dashboard/src/types/*.ts`)을 먼저 보고 맞췄다 → [[flask]]. 모델 라벨 순서의 정본은 서버 코드 쪽 목록이고, 모델 폴더의 라벨 파일은 대조 대상일 뿐이다 → [[대조-가드]]

## 언제 쓰나 (상황 예시)
- 혼자 여러 AI 채팅방과 도구를 오가며 장기 프로젝트를 할 때.
- 사람용 대시보드(노션 등)와 기계가 추적하는 기록(Git)을 함께 쓸 때 어느 쪽이 이기는지 정해야 할 때.
- 오래전에 "검증 완료"라고 적어 둔 항목을 다시 쓸 때. 그 사이 환경이 바뀌었는지 먼저 본다.
- 모델 라벨 순서, 클래스 목록처럼 서버·모델·테스트·데모 데이터가 함께 쓰는 값을 다룰 때.

## 실습에서 배운 것 / 트러블슈팅
- 운영 체계를 짜는 데 하루를 쓰고, 매일 루틴도 30~40분이 추가된다. 그래도 "어디까지 했더라?"를 반복하는 비용이 더 크다고 판단했다.
- **같은 수치가 두 곳에 적히면 한쪽만 갱신된다 (2026-05-12)**: 실측값이 한 절에만 들어가고 다른 절에는 추정값이 남아 같은 문서 안에서 값이 충돌했다.
- **정적 기록은 시간이 지나면 현실과 어긋난다**: 정본에 적힌 사실도 "마지막으로 확인한 시점의 스냅샷"이다.
  - 문서의 pio venv 경로 `/tmp/pio-venv` → macOS 재부팅으로 사라짐 → [[platformio]]
  - "env:poc 컴파일 SUCCESS" → 그 뒤 파일이 늘어 깨짐 → [[platformio]]
  - "로컬 main = remote main" → 웹 squash 머지로 깨짐 → [[github-flow]]
- **결정 문서와 코드값이 어긋났던 사례 (기록 43)**: 문서는 "신뢰도 70% 미만이면 미전송"인데 서버 상수는 `0.6`이었다. 데모 시드는 임계값 로직을 안 타서 화면엔 티가 안 났다. `0.6 → 0.7` 한 줄로 고쳤다. 비교가 `if top < CONFIDENCE_THRESHOLD`(strict `<`)라 0.70은 발송, 0.699는 미전송으로 문서와 정확히 일치한다. 발표 값과 코드 값이 다르면 버그가 아니라 신뢰의 문제다.
- **라벨 인덱스 한 곳 관리 (기록 41)**: 서빙 출력 인덱스(doorbell=0 / knock=1 / fire_alarm=2)는 config의 `CLASSES`를 그대로 상속한다 → [[keras-savedmodel]]
- **결정은 안 읽히는 상수가 아니라 주석으로 (기록 43)**: SpecAugment 미적용 결정을 상수로 박으려다 그 상수를 아무도 읽지 않는다는 걸 확인했다. 읽히지 않는 상수는 죽은 코드라, 배선 지점에 "왜 미루는지 + 나중에 어디를 켜면 되는지"를 주석으로 남겼다 → [[data-augmentation]]
- **코드에서도 판단 로직은 한 곳에 (기록 49)**: 판단 로직을 두 경로에 복사하면 정책이 바뀔 때 한쪽만 고치는 실수가 난다 → [[대조-가드]]
- **주석이 거짓말을 하는 것도 버그다 (기록 52·55)**: "이 코드는 앱과 분리돼 있다"는 설명이 옛말이 됐고, "A 방식으로 하면 된다"는 주석 4곳이 조사로 B가 맞다고 밝혀진 뒤에도 남아 있었다.
- **"이미 그렇다"와 "우리가 그렇게 했다"를 구분해 쓴다 (기록 56)**: "설정 주석 처리로 기능 활성"이라는 관찰 문장이 한 달 뒤 행동으로 읽혀, 있지도 않은 과제가 6일간 최우선 블로커로 올라 있었다 → [[미결-실재-확인]]
- **정확한 문장이 요약되며 틀린 문장이 됨 (기록 62)**: 원문은 "이 항목은 별도 관리표에는 없다(기록 문서가 단독 관리)"로 맞는 문장이었다. 요약에서 "A·B·C·그리고 이 항목과 동일하게 처리"로 묶였는데 A·B·C는 진짜 어디에도 없는 항목이었다. 그 묶음 때문에 4일간 여러 작업 지시에 틀린 전제가 들어갔다.
  - 재발 방지: 여러 항목을 한 목록에 묶을 때 그 목록의 술어가 항목마다 참인지 하나씩 확인한다. "~와 동일하게", "같은 이유로"가 특히 위험하다.
- **출처가 틀린 인용 (기록 62)**: "결정 문서 몇 절에 있다"던 원칙 셋이 실제로는 테스트 코드 주석에 있었다. 저장소 전체를 대상으로 문장 일부를 검색하면 위치가 바로 나온다. 이런 인용 오류는 누적 13건이었다.
- **이력 숫자와 현재 숫자 가르기 (기록 62)**: "옛 숫자를 전부 최신 값으로 고쳐라"는 지시에서 다섯 곳 중 네 곳은 "그때 그 작업에서 N건"이라는 이력 서술이었다. 숫자를 만나면 "지금 값인가, 그때 값인가"부터 가른다.
- **"돌릴 수 있는 도구"와 "돌렸다는 기록"은 다르다 (기록 58)**: "기존 회귀 검사 세트를 다시 돌려라"라고 적었는데 그런 파일이 없었다. 이번에 실제 파일로 30개 케이스를 남겼다.
- **클래스 목록 (기록 93)**: 데모 데이터 테스트는 서버 쪽 단일 출처를 읽는다. 테스트가 읽지 않는 목록을 바꿔도 테스트가 통과해서, 그 위치를 바꾸는 건 효과 없는 조작임을 확인했다.
- 한계: 펌웨어 헤더와 서버 상수처럼 두 곳에 따로 적힌 값은 여전히 사람이 같이 고쳐야 한다. 대조 테스트는 어긋남을 드러낼 뿐이다.
