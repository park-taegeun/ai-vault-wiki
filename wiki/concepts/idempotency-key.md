## 한 줄 정의
요청마다 번호를 붙여, 서버가 같은 번호의 요청을 다시 받으면 새로 처리하지 않고 이전 결과를 돌려주게 하는 방식이다. 중복 전송으로 같은 일이 두 번 처리되는 걸 막는다.

## 핵심 내용
- [[띵동]] 서버는 ESP32가 발급한 `client_request_id`를 `idempotency_keys` 테이블에 24시간 보관하고, 같은 번호가 오면 이전 응답을 그대로 replay한다 → [[flask]], [[sqlalchemy]]
- 덕분에 펌웨어 재시도 로직을 "응답 못 받으면 그냥 재시도"로 단순하게 둘 수 있다.
- 위험은 번호 중복 자체가 아니라, **새 소리를 보냈는데 어제의 판정이 돌아오는 것**이다.

## 언제 쓰나 (상황 예시)
- 네트워크가 불안정한 기기가 재시도할 수 있는 요청(알림 트리거 등)을 보낼 때.
- 클라이언트 시간 제한이 서버 처리보다 짧아 "서버는 성공, 기기는 못 들음"이 생길 수 있을 때 → [[http-timeout]]

## 실습에서 배운 것 / 트러블슈팅
- **설계 (2026-06-14, PR #2)**: curl 검증에서 같은 key의 재요청이 200 replay로 돌아오는 것을 확인했다.
- **터널 실험 (2026-09-09)**: 같은 요청을 두 번 보내면 재처리가 차단되는 걸 실제 경로에서 확인했다.
- **재부팅하면 같은 번호가 다시 나온다 (2026-10-07)**: 기기 카운터가 재부팅 후 1부터 다시 시작해 어제와 같은 번호를 만들 수 있었다. 번호 앞에 부팅마다 새로 뽑는 난수를 붙였다. 재부팅 전후로 앞자리가 바뀌는지, 새 번호의 첫 응답이 옛 판정 재생이 아닌 새 요청 응답인지를 실험으로 확인했다.
- **기기 고유값을 쓰지 않은 이유**: 재부팅해도 그대로라 막으려던 충돌을 못 막는다.
- **전송 간격 제한은 별개**: 5초 안에 다시 보내면 첫 번째 201, 두 번째 429로 거절되고 기기는 재시도하지 않는다(서버 기록으로 확인).
- **사진 카드 두 장 (기록 84, 미해결)**: 메신저 발송 시간 초과 뒤 재시도가 사진을 한 장 더 보낸 것으로 추정된다. 서버 → 메신저 구간에는 이런 중복 방지가 없다 → [[kakaotalk-message-api]]
