## 한 줄 정의
요청마다 번호를 붙여, 서버가 같은 번호의 요청을 다시 받으면 새로 처리하지 않고 이전 결과를 돌려주게 하는 방식이다. 중복 전송으로 같은 일이 두 번 처리되는 걸 막는다.

## 핵심 내용
- [[띵동]] 서버는 ESP32가 발급한 `client_request_id`를 `idempotency_keys` 테이블에 24시간 보관하고, 같은 번호가 오면 이전 응답을 그대로 replay한다 → [[flask]], [[sqlalchemy]]
- 덕분에 펌웨어 재시도 로직을 "응답 못 받으면 그냥 재시도"로 단순하게 둘 수 있다.
- 위험은 번호 중복 자체가 아니라, **새 소리를 보냈는데 어제의 판정이 돌아오는 것**이다.
- **왜 이런 장치가 필요한가 (HTTP 메서드의 멱등성)**: 같은 요청을 여러 번 보내도 결과가 같으면 멱등하다. 리소스를 통째로 덮어쓰는 PUT은 멱등하지만, "age를 1 올려라" 같은 PATCH는 보낼 때마다 결과가 달라진다. 멱등하지 않은 요청이 재전송되면 같은 일이 여러 번 반영되므로, 요청 번호로 "이미 처리한 요청"을 알아보게 한다. → [[rest-api]]

## 언제 쓰나 (상황 예시)
- 네트워크가 불안정한 기기가 재시도할 수 있는 요청(알림 트리거 등)을 보낼 때.
- 클라이언트 시간 제한이 서버 처리보다 짧아 "서버는 성공, 기기는 못 들음"이 생길 수 있을 때 → [[http-timeout]]

## 실습에서 배운 것 / 트러블슈팅
- **설계 (2026-06-14, PR #2)**: curl 검증에서 같은 key의 재요청이 200 replay로 돌아오는 것을 확인했다.
- **터널 실험 (2026-09-09)**: 같은 요청을 두 번 보내면 재처리가 차단되는 걸 실제 경로에서 확인했다.
- **재부팅하면 같은 번호가 다시 나온다 (2026-10-07)**: 기기 카운터가 재부팅 후 1부터 다시 시작해 어제와 같은 번호를 만들 수 있었다. 번호 앞에 부팅마다 새로 뽑는 난수를 붙였다. 재부팅 전후로 앞자리가 바뀌는지, 새 번호의 첫 응답이 옛 판정 재생이 아닌 새 요청 응답인지를 실험으로 확인했다.
- **기기 고유값을 쓰지 않은 이유**: 재부팅해도 그대로라 막으려던 충돌을 못 막는다.
- **전송 간격 제한은 별개**: 5초 안에 다시 보내면 첫 번째 201, 두 번째 429로 거절되고 기기는 재시도하지 않는다(서버 기록으로 확인).
- **전송 제한 5초 → 2.5초, 감이 아니라 산술로 (기록 99)**: 중간 발표 시연에서 같은 기기 5초 제한에 걸려 거절된 요청이 있었다. 처음엔 직감으로 4초가 권해졌지만, 그날 로그의 거절 33건을 따져 보니 4초는 22건만 반드시 통과시켰다.
  - 원인: 서버는 오디오 업로드가 끝난 뒤에 시각을 찍는다. 망이 느리다가 빨라지면 서버가 느끼는 간격이 실제보다 짧아진다. 33건의 간격 하한 중 최솟값은 3,026ms였다.

  | 한도 | 거절 33건 중 반드시 통과 | 여유 |
  |---|---|---|
  | 5초 | 1 | |
  | 4초 | 22 | |
  | 3.5초 | 28 | |
  | 3초 | 33 | 26ms |
  | 2.5초 | 33 | 526ms |

  - 3초는 숫자상 전부 통과지만 여유가 26ms뿐이라, 여유 526ms인 2.5초를 잠정값으로 골랐다. 보드가 다음 요청까지 기다리는 시간(약 5.06초)과 짝이 맞는지는 테스트로 묶어 한쪽만 바꾸면 실패하게 했다 → [[대조-가드]]
  - 업로드가 끝난 뒤 시각을 찍는 구조는 그대로라 거절이 다시 나지 않는다는 보장은 아니다. 값을 바꾸자는 권고는 그 값을 가르는 원 로그를 먼저 계산한 다음에 한다.
  - 시연 날 2.5초 제한에서 거절이 1건 있었다. 망 지연 탓인지 가를 보드 기록이 없어 재판정하지 못했고, 값은 잠정인 채로 끝났다(기록 100).
- **사진 카드 두 장 (기록 84)**: 메신저 발송 시간 초과 뒤 재시도가 사진을 한 장 더 보낸 것으로 추정된다. 서버 → 메신저 구간에는 이런 중복 방지가 없다. 기록 99에서 사진 응답 대기 시간 초과만 재시도에서 빼는 수정을 넣었지만, 확인한 날 시간 초과가 0번이라 효과는 미확인이다. 시연 날 이 분기가 1번 돌았지만 사진 도착과 중복 여부는 확인하지 못했다(기록 100) → [[kakaotalk-message-api]]
