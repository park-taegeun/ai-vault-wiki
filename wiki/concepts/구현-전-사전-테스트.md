## 한 줄 정의
본격 개발 전에 실제 데이터로 작은 스크립트를 돌려 설계의 핵심 가정이 맞는지 수치로 확인하는 단계다. [[띵동]]에서는 발표 피드백("선례를 찾고 사전 테스트 방법을 고민하라")에 대한 답으로 2026-04-27에 처음 했고, 이후 "만들기 전에, 재기 전에 한 번 더 확인한다"는 습관으로 이어졌다.

## 핵심 내용
- **첫 사전 테스트 (2026-04-27)**: 공개 환경음 WAV, 초인종/노크/화재경보 각 10개(총 30개). 합성 신호는 쓰지 않았다.

| 가정 | 테스트 | 결과 | 판단 |
|---|---|---|---|
| YAMNet으로 3종 분류 가능? | A. pre-trained 한계 | Top-1 20~40% | Fine-tuning 필수 → [[yamnet]] |
| SP/DTW + cosine이 초인종을 구분? | B. 변별력 | 화재경보 분리 마진 8.418 | 설계 타당 → [[초인종-유사도-검증]] |
| 5초 이내 알림? | C. 지연시간 | 파이프라인 평균 61.7ms | 여유 있게 달성 |
| (보조) 임계값 설정 | D. 오탐/미탐 시뮬레이션 | 전 구간 오탐 0%, 미탐 80~100% | Fine-tuning 후 재분석 |

- **테스트 C 상세** (로컬 모의 실행, 100회, MacBook Pro M4):

| 단계 | 평균(ms) | 최대(ms) |
|---|---|---|
| WAV 로딩·전처리 | 0.4 | 1.1 |
| 멜 스펙트로그램 변환 | 4.4 | 27.9 |
| YAMNet 추론 | 35.1 | 117.5 |
| SP/DTW 계산 | 21.8 | 38.0 |
| 전체 | 61.7 | 150.1 |

  전체 추정은 ESP32 패키징 ~0.2초 + HTTPS 전송 ~0.3~0.5초 + Nginx/Gunicorn ~0.05초 + ML 0.062초 + 카카오톡 ~0.3~0.5초 = 약 1.0~1.3초였다.
- **"가능성 높음"이 붙은 말은 싸게 갈라 볼 실험이 있는지부터 본다 (기록 78)**: 확인이 아니라 추측인 권고 위에 몇 시간짜리 작업을 쌓기 전에 한두 시간짜리 실험을 먼저 한다.

## 언제 쓰나 (상황 예시)
- 설계가 이론상 그럴듯해서 바로 구현으로 넘어가고 싶을 때. 그 자신감 자체가 리스크다.
- 발표·심사에서 "그게 될 거라는 근거가 뭐냐"에 답해야 할 때.
- 측정 코드, 쪼개기 로직, 글자 상한 같은 것을 짜기 전에 그 전제가 맞는지 볼 때.

## 실습에서 배운 것 / 트러블슈팅
- **오탐률 0%를 좋은 결과로 읽지 말 것**: pre-trained 모델이 모든 클래스에 낮은 확률을 분산해서 대부분 걸러졌다. 틀린 알림을 안 보낸 게 아니라 아무 알림도 안 보낸 것이다. 오탐은 미탐률과 함께 본다.
- 결론적으로 해결할 과제가 Fine-tuning 하나로 좁혀졌다 → [[transfer-learning]], [[현관-소리-학습-데이터]]
- **측정 코드를 짜기 전에 전제부터 (기록 50)**: 사진 포함 알림 왕복을 재려고 문서를 다시 보다가, "나에게 보내기"가 URL만 받는다는 걸 측정 코드를 짜기 직전에 발견했다 → [[kakaotalk-message-api]]
- **음성 인식 제품 통합 (기록 52·53)**: 신청 상태를 보러 콘솔에 들어갔다가 서비스가 다른 제품으로 통합됐다는 안내를 봤다. 실측을 미루고 "제품 재검토 필요"만 기록했다. 자료 조사는 "기존 서비스가 맞을 것 같다"까지 데려다줬고, "지금 신규 신청이 되는가"는 신청 화면을 봐야만 답할 수 있었다 → [[asr]]
- **받을 준비를 앞당기기 (기록 53)**: 녹음이 오기 전에 측정 도구가 파일 이름의 초인종 정보를 읽게 고쳐, 녹음이 들어오면 명령 한 줄로 측정이 돌게 했다 → [[대조-가드]]
- **30분 터널 실험 (기록 57)**: 전수 점검이 "외부 서버가 유일한 선행조건"이라 결론 냈지만, 임시 공개 통로로 로컬 서버를 열어 보니 요청 응답 → 사진 업로드·공개 주소 발급 → 메신저 사진 도착까지 전 구간이 통과했다. 고친 코드는 0줄이었다. 예전에 그 부분을 설정값으로 빼 둔 덕이었다. 통로는 임시 주소라 정식 배포가 아니라 안전망으로만 둔다 → [[ai-산출물-검증]]
- **임계값은 코드에 넣기 전에 실측표 전부 대입 (기록 57)**: ToF 후보 기준값이 "A와 B 사이"라 적혀 있었지만 실제로는 B보다 컸다 → [[vl53l5cx]]
- **쪼개기·글자 상한을 짜기 전에 보내 보기 (기록 58·60)**: 문서상 길이 제한을 넘는 266자 화재 안내문이 실제로는 잘리지 않았다. 15/52/110자로 보내 보니 사진 카드는 글자 수가 아니라 두 줄에서 잘렸다. 같은 등급의 문서 근거가 한 번은 뒤집히고 한 번은 맞았다. 원칙은 "문서를 믿지 마라"가 아니라 "근거의 등급이 결과를 정하지 않으니 매번 재본다"다.
- **발표 당일 리허설 절차 (기록 60)**: 통로 켜기 → 새 주소 확인 → 설정 교체 → 서버 재시작 → 관통 확인 순서를 문서로 확정했다. 관통 확인을 안 하면 사진이 안 뜰 때 통로 문제인지 메시지 앱 문제인지 갈리지 않는다.
- **구현 전에 머릿속 설명부터 잰다 (기록 75)**: 자동 촬영 트리거를 만들기 전 하루 동안 마이크를 재 보니, 남은 건 기능이 아니라 틀린 설명의 목록이었다 → [[마이크-튐-판별]]
- **절차를 짜기 전에 기기가 언제 움직이는지 로그로 본다 (기록 77)**: 코드를 읽고 "버튼 → 서버 응답 → 녹음 시작"이라 생각했지만, 녹음은 버튼을 누른 순간 시작했다. 절차를 "준비 신호 → 1초 기다림 → 버튼 → 초인종 누르기"로 바꿨다.
- **상태 변화는 바뀐 값으로 판정 (기록 77)**: "리셋했다"는 답만 믿고 녹음했다가 반쪽이 사라졌다. 이후 판정 기준은 센서 프레임 번호가 다시 시작했는지, 요청 ID 앞부분이 바뀌었는지다.
- **서버 정규화 실험 (기록 78)**: "서버에서 입력 음량을 학습 때와 같게 맞춰 주면 해결될 가능성이 높다"는 권고를 실험으로 갈랐다. 실제 추론·발송 경로를 그대로 두고 입력 변환 하나만 바꿨다.

| 입력 | 원본 | 정규화 |
|---|---|---|
| 초인종 17구간 발송 | 16 | 16 |
| 무음 19구간 화재 발송 (사람 없음 가정) | 0 | **12** |
| 분포 밖 126건 발송 (사람 있음 / 없음 가정) | 102 / 20 | 57 / 14 |
| 시험 세트 424건 정답 | 376 | 376 (바뀐 판정 0) |

  - 정규화는 무음에서 마이크 잡음 바닥을 소리처럼 키워 화재로 바꿨다. 권고는 뒤집혔다.
  - 실험이 질문을 바꿨다. 원본 조건에서 모델은 기기 무음 19개를 전부 노크로 분류했다(신뢰도 0.80~1.00). 기기 자체의 조용함이 이미 분포 밖이었다. 대응은 서버가 아니라 학습 데이터 쪽으로 정했다 → [[현관-소리-학습-데이터]], [[out-of-distribution]]
  - "이 조건에서 서버 정규화는 해결책이 아니었다"까지만 말한다.
- **돌리기 전에, 나올 숫자가 무엇의 숫자인지 계산 (기록 82)**: 재학습 전에 해시 배정 규칙을 다시 짜서 미리 계산했다. 계산기를 믿기 전에 전날 실제 배정과 대조해 6/6 일치를 먼저 확인했다. 결과 보드 노크가 평가 쪽에 0개여서 평가 전용 노크 녹음을 추가하기로 했다. 확인의 층위 앞에 "검사에 넣는 입력이 맞는가"가 있다.
- **새 도구는 정답을 아는 입력으로 먼저 (기록 82)**: 측정 도구는 서버와 같은 분류 경로를 타되 발송은 하지 않고 "발송됐을 건수"만 센다. 확신도 1.0 초인종 클립을 넣어 확인하고, 같은 입력 두 번에 출력이 글자 단위로 같은지를 단정 항목에 넣었다.
