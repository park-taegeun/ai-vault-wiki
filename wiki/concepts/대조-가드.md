## 한 줄 정의
"지금 맞는 값"을 "어긋나는 순간 시끄럽게 실패하는 값"으로 바꾸는 장치다. 변경 전후 같아야 하는 결과, 또는 두 곳에 따로 사는 같은 값을 원본끼리 직접 대조해 "안 바뀌었다 / 같다"를 증명한다. [[띵동]]에서 반복해 쓴 습관이다.

## 핵심 내용
- 목적은 "새 기능이 된다"가 아니라 "기존 것이 한 톨도 안 변했다"를 보이는 것이다. 위치만 옮겼다고 믿어도 옮기는 중에 조건 하나가 어긋날 수 있다.
- 비교 단위를 결과 개수가 아니라 **내용 전체**로 잡는다. 개수가 같아도 안의 내용이 뒤바뀌었을 수 있다.
- "지금 같다"는 보증이 아니다. 두 곳에 따로 적힌 값은 한쪽만 고치면 아무도 모른다. 위험한 쪽은 틀리면 터지는 쪽이 아니라 **틀려도 조용히 도는** 쪽이다.
- 가드는 어긋남을 드러낼 뿐, 두 곳을 사람이 같이 고쳐야 하는 구조를 없애지는 않는다 → [[single-source-of-truth]]
- 가드 자체도 일부러 부러뜨려 진짜 잡는지 본다 → [[fault-injection]]

| 상황 | 대조 방법 | 결과 |
|---|---|---|
| 판단 로직을 무작위 생성 함수에서 떼어냄 (49) | 분리 전·후 코드를 500가지 조건으로 나란히 실행 | 500건 모두 일치 |
| 라이브러리 버전 고정을 범위로 완화 (52) | 실제 설치 후 해석된 버전 + 소리 디코딩 결과를 예전 기록과 비교 | 같은 버전, 같은 값 |
| 측정 도구에 파일 이름 읽기 추가 (53) | 묶인 내용 전체를 하나의 지문값으로 뽑아 전후 비교 | 완전히 같음 |
| 펌웨어에 진단 도구 추가 (54) | 기존 구성 3개 재빌드 | 결과물 용량 바이트 단위 동일 |
| 펌웨어에 연속 확인 안전장치 추가 (55) | 무관한 설정 재빌드 | 결과물 바이트 단위 동일 |
| 라이브러리 파일을 손댄 적 있는지 (56) | 배포 원본 세 버전 + 로컬 파일 지문값 대조 | 모두 일치 |
| 클래스 병합 라이브러리 전역 설정 변경 (74) | 모든 호출 조합(28행)의 결과를 전후 비교 + 토큰 677종 프로브 | 8행 변화, 전부 개선 방향·악화 0 |
| 서버 입력 정규화 실험 도구 (78) | 원본 조건이 이전 기준값을 재현하는지 행 단위 비교 | 불일치 0 / 126 |

## 언제 쓰나 (상황 예시)
- 리팩터링으로 로직의 위치만 바꿀 때.
- 예전 측정치와 앞으로 뽑을 측정치를 나란히 비교해야 할 때. 측정 도구가 바뀌면 비교가 깨진다.
- 모델을 교체하기 전에 라벨 순서를 확인할 때.
- 펌웨어 헤더와 서버 상수처럼 같은 값이 두 코드베이스에 있을 때.
- 주석만 고친 변경이 정말 동작을 안 바꿨는지 증명할 때.

## 실습에서 배운 것 / 트러블슈팅
- 새로 넣는 부분은 어긋날 만한 입력을 미리 검사에 넣었다(기록 53): 번호 없는 파일, 구분자가 여러 개인 이름, 빈 폴더, 대소문자 차이. 기존 계산은 한 줄도 안 건드렸다.
- 로직만 검증한 것과 실전 확인은 다르다(기록 49). 가짜 점수 3종으로 판단 로직만 검증하고 "로직 검증 완료, 실전 확인 대기"로 적었다.
- **전역 설정은 고친 지점이 아니라 모든 호출 조합이 기준 (기록 74)**: 고친 곳만 보면 나머지가 조용히 바뀐다. 규칙은 "개선 방향은 허용, 악화 방향이 하나라도 있으면 정지"였다 → [[design-tokens]]
- **도구부터 믿을 수 있게 (기록 78)**: 원본 조건이 알려진 기준값을 재현하지 못하면 그 도구의 결과는 읽지 않는다는 조건을 결과를 보기 전에 걸었다.
- **"변화 없음"이 대조군이 된다 (기록 78)**: 시험 세트 424건은 정규화해도 판정이 0건 바뀌었다(확률 차이 최대 2.3×10⁻⁵). 그래서 무음에만 큰 차이가 났을 때 도구 오류가 아니라 입력 때문이라고 말할 수 있었다 → [[구현-전-사전-테스트]]
- **공유 함수를 바꾸기 전에 호출부마다 입력을 본다 (기록 80)**: 튐 마스크 처방을 위임했는데, 에이전트가 착수 전 대조에서 멈추고 보고했다. 그 함수를 배경 녹음 도구뿐 아니라 노크·초인종 도구도 쓴다는 것이었다. 그대로 적용했다면 노크·초인종 쪽만 큰 소리가 지워졌을 것이다. 에러도 없고 테스트도 통과한 채로 → [[마이크-튐-판별]]
- **스윕도 실제 함수로 (기록 81)**: 판정 함수를 재구현하지 않고 실제 도구 함수를 그대로 불렀다. 재구현 차이가 결과에 섞이지 않게 하려는 것이다 → [[onset-detection]]
- **라벨 순서 기동 가드 (기록 92)**
  - 기존 검사는 출력 **개수**만 봤다. 순서가 틀린 모델은 개수가 맞아 통과하고 화재경보·초인종이 뒤바뀐 채 돌 수 있었다.
  - 동작: 목록 파일 없음(옛 모델) → 경고 후 기동 / 순서까지 일치 → 경고 한 줄 후 기동 / 불일치나 깨진 파일 → 모델 올리기 전 기동 실패.
  - 실제 모델 폴더 셋 모두 순서 일치. 일부러 순서를 뒤집은 임시 폴더는 기동 실패.
- **펌웨어↔서버, 녹음↔학습 도구 대조 테스트 (기록 92)**: 센서 영역 수 64 ↔ 64, 묶음 수 16 ↔ 16. 녹음 파일 이름 규칙은 60조합이 양쪽에서 같게 읽혔다. 녹음 도구는 import하면 서버 설정까지 읽어서, 코드를 실행하지 않고 구문 트리로만 읽어 대조했다. 유닛 이름 밑줄 금지 규칙은 맞았지만 주석에 적힌 이유가 틀려서 바로잡았다.
- **응답 크기 예산 테스트 (기록 92)**: 현관 기기의 고정 버퍼 유효 용량은 767바이트다. 보수 최악 응답 737 ≤ 767, 여유 30바이트였다.
  - 문서에 따로 적힌 686, 689, 693과 새 737은 틀린 게 아니라 **세는 정의가 달랐다**. 689는 도달 가능한 한 조합 손계산, 737은 도달 불가 조합까지 넣은 보수 상한이었다.
  - 서버를 디버그 모드로 띄우면 들여쓰기 출력으로 890바이트가 되어 예산을 넘는다.
  - 같은 이름의 숫자는 "무엇을 어떻게 셌는가"부터 맞추고, 사전 계산 스크립트도 남긴다.
- **데모 데이터 계약 테스트 (기록 93)**: 클래스가 4종인데 데모 데이터는 점수 키가 3개였다. 테스트 3개(키 집합 = 서버 클래스 목록, 점수 합 1.0, 신뢰도 = 예측 클래스 점수)를 넣었고, 일부러 깨는 확인 5종을 전부 검출했다. "닫힌 3종" 주석은 숫자만 바꾸지 않고 값이 어디까지 가는지 따라가 "분류는 4종, 알림 문구까지 가는 건 3종"으로 다시 썼다.
- **빌드 해시 불변식 (기록 94)**: 대시보드 주석 두 줄만 고치면서 빌드 산출물 7개 파일의 해시가 같아야 한다는 불변식을 걸었다. 먼저 고치기 전 코드를 두 번 빌드해 결정성부터 확인했다. 주석에 스타일 유틸리티 이름과 같은 낱말을 넣으면 CSS 해시가 달라졌다(스타일 도구가 주석 속 낱말도 읽음).
