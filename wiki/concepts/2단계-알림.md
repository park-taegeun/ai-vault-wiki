## 한 줄 정의
[[띵동]]에서 소리 감지 알림을 두 번에 나눠 보내는 구조다. 1차는 5초 안에 "무슨 소리가 났다"만, 2차는 처리가 끝난 뒤 방문자 사진과 음성 자막을 보낸다.

## 핵심 내용
- **왜 나눴나 (2026-04-29)**: 카메라 캡처와 STT가 들어오면서 흐름을 단계별 시간으로 쪼개 보니 합계가 9~17초였다(STT용 녹음 3~5초, 업로드 1~3초, 서버 YAMNet+STT 2~5초 등). "감지 후 5초 이내"를 알림 한 번으로는 지킬 수 없었다.

| 안 | 내용 | 기각/채택 이유 |
|---|---|---|
| A | 녹음을 5초 → 2초로 단축 | 자막이 "택배요" 정도로 짧아져 STT 기능의 가치가 떨어짐 |
| **B** | **1차/2차 분리** | **채택.** 5초 목표 유지, 실제 사용 흐름(빨리 알고 → 나중에 자세히)과 맞음 |
| C | 요구사항을 10초로 완화 | "왜 늘렸나"를 설명할 근거가 약함 |

- **옵션 B를 고른 이유 네 가지 (2026-04-29)**
  1. **시연 임팩트**: "띵동 → 5초 후 카톡 → 잠시 후 누가 왔는지 사진+자막"으로 놀라는 순간이 두 번 생긴다.
  2. **차별화**: 4/29 피드백 1순위와 맞는다. 다른 시스템은 1차 알림에서 끝나지만 이 시스템은 2차 알림으로 차별화된다.
  3. **5초 목표 유지**: 요구사항을 고치지 않아도 된다.
  4. **실제 사용 흐름**: 빨리 "누가 왔다"를 알고, 좀 있다가 자세한 정보를 보는 흐름이 어색하지 않다.
  - 단점인 "메시지가 두 번 온다"는 같은 스레드 안에 이어지는 메시지로 디자인해서 해결한다(1차 "초인종 감지", 2차 "방문자: [사진] / '택배입니다'").

- **1차**: 소리 분류 직후 텍스트 알림(예: "누군가 노크했어요"), 목표 5초 이내.
- **2차**: 방문자 사진 + 방문자 발화를 STT로 옮긴 자막, 목표 15초 이내(PoC 실측 전 잠정값).
- **컨셉**: "기존 알림이 '띵동'으로 끝났다면, 본 시스템은 누가 와서 뭐라고 했는지까지 알려준다." 인터폰으로 "누구세요?"를 듣지 못하는 사용자가 문을 열기 전에 방문자를 확인하게 한다.
- **화재경보는 다르게**: 사람 검증을 우회해 즉시 1차만 보내고, 정부 지정 화재 대응 수칙을 함께 보낸다. 안내방송을 못 듣고 검색할 여유도 없기 때문이다.
- **API에서의 분리**: 1차는 `POST /api/v1/detect`(알림 저장 + `request_id` 발급), 2차는 `POST /api/v1/enrich`(사진 + 추가 5초 녹음). 엔드포인트를 나눠 1차가 2차를 기다리지 않는다. 2차 요청에는 1차 응답의 id를 붙인다 → [[flask]], [[sqlalchemy]]

| 설계 항목 | 결정 | 이유 |
|---|---|---|
| 사람 검증 위치 | ESP32에서 먼저 | 오탐 트래픽 차단, 카메라가 사람 감지 때만 켜지는 프라이버시 논거 |
| 2차 처리 | 단순 동기 | 시연 환경엔 동시 트래픽 없음, 워커 2개로 충분 |
| 이미지 저장 | 서버 로컬 디스크 | 추가 비용 없음, 30일 보존 |
| 2차 실패 | best-effort + 1회 재시도 | 실패 알림을 또 보내면 노이즈 |

## 언제 쓰나 (상황 예시)
- 빠른 반응과 무거운 후처리가 한 요구사항 안에 섞여 있을 때. 즉시 알릴 최소 정보와 나중에 붙일 풍부한 정보를 나누면 시간 목표를 낮추지 않아도 된다.
- 사전 필터(사람 검증 등)가 안전 관련 이벤트까지 막지 않는지 클래스별로 다시 확인할 때.

## 실습에서 배운 것 / 트러블슈팅
- **ToF를 차단 조건에서 메타데이터로 (2026-05-06)**: 처음 흐름은 "사람이 없으면 ESP32가 전송을 막는다"였다. 화재경보는 사람이 누르는 게 아니라 저절로 울리므로 사람이 없을 때 누락될 수 있었다. 그래서 ToF 결과를 서버에 붙여 보내고, 서버가 클래스별로 정책을 나눈다.
  - 화재경보: ToF 무시하고 무조건 진행
  - 노크: ToF 사람 검증
  - 초인종: ToF 사람 검증 + (등록된 경우) [[초인종-유사도-검증]]
- **2차의 출발 (2026-05-09)**: 2026-04-29 발표 피드백("차별화 포인트가 필요하다")에 대한 대응으로 도어캠 + 음성 자막을 붙였다. STT는 공개 벤치마크의 인터폰급 노이즈 CER을 근거로 골랐다 → [[asr]]. 2026-05-13 발표에서 시나리오 v1 그대로 확정했다.
- **STT 비용 (2026-05-16)**: 단가 초당 0.5원(분당 30원). 2차 알림 때 5초 추가 녹음 패턴으로 추정한 사용량은 월 1,000~3,000원으로, 학생 크레딧 기본 100,000원 안에 충분했다.
- **지연 계측을 실제 타임스탬프로 (2026-07-06)**: 대시보드 타이밍 카드가 `0ms / 0%`였던 건 stats가 timing을 하드코딩 0으로 반환했기 때문이었다. 실제 타임스탬프 델타로 집계하게 고쳤다(`primary_sent_at - detected_at`, 미발송 건 제외, 분모 0 방어) → [[화면이-아는-만큼만-말하기]]
- **5초 예산 구간별 실측**

| 구간 | 결과 | 출처 |
|---|---|---|
| AI 추론 (서버) | p95 6.74ms (예산의 0.13%) | 기록 44 |
| 서버 소리 해독 | 0.038ms (440Hz 사인톤 64,000바이트 → 32,000샘플, RMS 0.353528 ≈ 이론값 0.5/√2) | 기록 45 |
| ESP32 업로드 64KB×14 (HTTP) | 최소 156 / p50 305 / p95 1043 / 최대 1879ms | 기록 46 |
| 카카오 "나에게 보내기" ×10 | p50 69.2 / p95 84.1ms | 기록 47 |
| ESP32 업로드 (HTTPS) ×14 | 전체 왕복 p50 1677 / p95 1863ms (예산의 40%) | 기록 48 |

  - 1차 체인 합계(암호화 없음)는 약 1.1초, 예산의 23%였다. 병목 기여도는 업로드가 92%였다.
  - 64KB 업로드는 TCP connect 270ms + POST 279ms로 연결 맺기가 절반이었다. 32KB 95.7ms, 64KB 318.3ms, 128KB 358.0ms로 크기를 두 배로 늘려도 지연이 거의 안 늘었다. 지연을 지배하는 건 데이터 양이 아니라 무선 왕복 오버헤드였다.
  - HTTP와 HTTPS 측정 사이의 어긋남은 [[https-tls]]의 모순 표시 참고.
- **병목 가설은 정밀하게 좁혀졌다**: (44) "업로드와 알림 왕복이 병목" → (46) "업로드 왕복은 빠르고 숨은 비용은 연결 수립" → (47) "업로드 하나가 병목의 대부분". 방향을 뒤집은 게 아니라 후보를 좁힌 정정이었다. 가설을 확정으로 적지 않았기에 가능했다 → [[ai-산출물-검증]]
- **전송 방식 (2026-07-09)**: multipart + 16비트 정수 원본 바이트(2초 = 64,000바이트). base64는 33% 부풀어서 피했다.
- **하드웨어 함정 (기록 46·48)**: IP가 접속마다 바뀜, 노트북이 핫스팟 주소를 엉뚱하게 받음, 업로드 도구와 상태 확인 도구의 포트 충돌 등 함정 다섯 개를 3시간 동안 뚫었다. 노트북 → 서버 가짜 요청으로 서버 계층을 먼저 통과시켜 두면 기기 실패 시 용의자가 기기 쪽으로 좁혀진다. 기기만 핫스팟에 거부당한 건 스마트폰 재부팅으로 풀렸다.
- 모든 측정은 로컬 노트북 서버 + 스마트폰 핫스팟 기준의 근사치다.
- **1차 판단 경로가 진짜가 됨 (2026-08-01)**: 서버의 소리 판단은 무작위 결과를 뽑던 자리표시자였다. 판단 로직(문턱값 비교, 화재경보 무조건 통과, 발송 여부)을 떼어내 가짜·진짜 경로가 공유하게 했다 → [[대조-가드]]. 합성 소리로 돌리니 최고 확률이 70% 아래라 "자신 없으면 안 보낸다"가 작동했다.
- 모델 첫 로딩이 길어서 서버 시작 시 미리 불러오고 예열한다. 시간을 없앤 게 아니라 요청 전으로 옮긴 것이라 시연 전에 서버를 켜 둬야 한다.
- **사진 공개 URL의 세 겹 안전장치 (2026-08-07)**: 카카오는 사진 파일이 아니라 URL만 받으므로 서버가 사진을 공개해야 한다. 현관 사진이라 주소 설계가 곧 프라이버시다 → [[kakaotalk-message-api]]
  1. 추측 불가능한 주소: 순번이 아니라 무작위 문자열로 발급한다.
  2. 로그인 없이 열림: 카카오가 가져가야 해서 인증을 걸 수 없다. 그래서 1번이 유일한 자물쇠다.
  3. 경로 탈출 차단: 엉뚱한 경로로 파일 시스템을 뒤지는 시도를 문자 검사로 막는다.
- 2차 업로드에는 사진 크기 상한과 파일 시작 부분의 고유 표식 검사를 더했다.
- **반올림이 알림 판정보다 앞에 있었다 (2026-10-07)**: 점수 `0.4 / 0.6 / 0.0`을 "표시 버그"로 의심했지만 정상이었다. 대신 반올림 위치를 따라가다 진짜 결함을 찾았다.
  ```
  지금:   점수 계산 → 반올림 → 알림 보낼지 판정
  원칙:   점수 계산 → 알림 보낼지 판정 → (표시용으로만) 반올림
  ```
  "0.70 미만은 안 보낸다"는 기준이 반올림된 값을 받아 0.695~0.69999가 통과할 수 있었다. 평가 데이터 424개 중 그 구간은 0건이라 수정 여부는 미정으로 남겼다. 원칙을 적는 일과 지켜지는지 확인하는 일은 별개다.
- **기기가 2차 알림을 처음 직접 보냄 (2026-10-08)**: 보드가 사진을 찍고 5초 녹음해 올리는 경로를 하루에 붙여 4회 실행했다. 보드 마이크로 한 실제 말("계세요 택배입니다 문 앞에 놓고 갈게요")이 그대로 글자로 돌아왔다(실제 육성은 1회). 4번째는 보드 시간 초과(15.5초)에 메신저 발송도 네트워크 도달 실패였다 → [[http-timeout]]
