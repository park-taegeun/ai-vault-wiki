## 한 줄 정의
TLS로 암호화한 HTTP다. 클라이언트는 서버 인증서를 검증해 상대가 진짜 서버인지 확인한다.

## 핵심 내용
- Let's Encrypt로 무료 SSL 인증서를 발급받아 도메인에 적용할 수 있다.
- [[nginx-gunicorn]] 구조에서는 Nginx가 인증서를 적용하고 복호화(SSL Termination)를 맡는다. 뒤쪽 내부 통신은 HTTP다.
- **암호화와 인증서 검증은 별개 단계다**: 임베디드 클라이언트(ESP32)는 `setInsecure()`로 서버 인증서 검증을 건너뛸 수 있다. 암호화는 되지만 중간자 공격을 막지 못한다.

## 언제 쓰나 (상황 예시)
- 기기가 클라우드 서버로 소리 파일·토큰 같은 데이터를 보낼 때.

## 실습에서 배운 것 / 트러블슈팅
- **결정 (2026-04-07)**: [[띵동]]은 Let's Encrypt + Nginx SSL Termination으로 정했다. ESP32의 `setInsecure()` 사용은 졸업작품 한계점으로 문서화하기로 했다.
- **PoC (2026-05-08)**: `WiFiClientSecure` + `setInsecure()`로 인증서 검증을 생략했다. 인증서는 서버가 먼저 올라와야 잡을 수 있어서 Let's Encrypt 적용은 11주차 [[flask]] 서버 구성 때로 미뤘다.
- **ESP32에서 TLS는 메모리 비용이 크다**: handshake 시점에 동적으로 약 80KB를 더 쓴다 → [[esp32-s3]] 메모리 예산에 반영했다.
- **HTTPS가 더하는 시간 실측 (기록 48)**: 14회 반복, 매번 새 연결. 서버는 로컬 노트북, 스마트폰 핫스팟.
  ```
  암호화 협상(14회, 매번 새 연결)  p50 678ms / p95 862ms
  연결 맺기: 암호화 없는 순수 연결 48~245ms, 암호화 포함 720~882ms
  데이터 올리기(64KB) 917~1105ms
  전체 왕복 p50 1677ms / p95 1863ms, 14회 전부 성공
  ```
  - 원문의 결론: **암호화는 연결 맺을 때만 비용이 붙고, 데이터 전송 자체는 늦추지 않는다.** 5초 예산 대비 p95가 20%(HTTP, 1043ms) → 40%(HTTPS, 1863ms)로 늘었지만 여유가 있다.
  - 연달아 다시 연결해도 협상 시간이 최초와 거의 같았다. 초인종은 몇 분~몇 시간 간격이라 연결 재사용(keep-alive)은 선택이지 필수가 아니다.
  - 재기 전에 계획을 줄였다. 인증서 종류별로 두 가지를 재려 했지만, 실제 서비스 방식은 사실상 하나였고 기기 계산 시간을 좌우하는 것도 인증서 종류가 아니었다.
  - TLS 1.2로 쟀다. 실제 배포 환경도 마이크 관련 구형 라이브러리 때문에 같은 소프트웨어를 써야 해서 측정 조건이 실제와 같았다.
  - 실제 클라우드 서버까지의 지리적 왕복은 빠져 있다. 이 숫자는 "암호화 계산 자체의 시간" 근사치다.

> [!warning] 모순
> 기록 46은 암호화 없이 64KB를 올리는 POST가 279ms(전체 p50 305ms)라고 적었다. 기록 48은 HTTPS로 64KB를 올리는 데 917~1105ms가 걸렸고 "지난번 암호화 없는 값과 거의 동일"하다고 적었다. 두 값이 맞지 않는다. 확인 필요.
