## 한 줄 정의
Andrej Karpathy가 제안한 패턴. LLM을 "사서"로 두는 개인 위키로, 사람은 원본을 넣고 질문만 하고, 정리·연결·유지는 LLM이 한다.

## 핵심 내용
- **3층 구조**
  | 층 | 이름 | 누가 쓰나 |
  |---|---|---|
  | 1층 | raw (원본) | 사람·수집기. 추가만, 수정 금지 |
  | 2층 | wiki (정리본) | LLM |
  | 3층 | schema (규칙서) | 사람 (예: `CLAUDE.md`) |
- **동작 세 가지**: Ingest(원본을 읽고 페이지 생성·보강), Query(위키를 인용하며 답변), Lint(끊긴 링크·고아 페이지·모순·중복 점검). 고아 페이지는 어디서도 링크되지 않은 페이지.
- **복리(compounding)**: 여러 글에 흩어진 같은 주제가 한 페이지에 누적된다. 예: MFCC를 다룬 연구 기록 4편(14·45·48·52편)이 [[mfcc]] 한 페이지로 모인다. 원본이 들어올수록 페이지가 두꺼워지고 링크가 는다.
- **복리를 숫자로 확인 (2026-10-19)**: 같은 비공개 5문항을 노션 자료를 넣기 전과 후에 질문마다 새 서브에이전트로 풀게 했다.
  | | 검색 적중 | 사실 정확 | 위키만으로 답함 |
  |---|---|---|---|
  | 넣기 전 | 1/5 | 4/5 | 1/5 |
  | 넣은 후 | 5/5 | 5/5 | 5/5 |
  넣기 전에도 사실은 4/5를 맞혔지만, 위키에 없어서 원본을 직접 뒤진 결과였다. 성장은 "못 풀던 문제를 풀게 됐다"보다 **같은 답을 더 싸고 빠르게 낸다**는 데 있다. RAG는 질문할 때마다 원본을 다시 찾지만, LLM Wiki는 정리 비용을 넣을 때 한 번만 내고 결과를 계속 재사용한다.
- **2차 확인 (2026-10-20)**: 노션 108개를 더 넣고(위키 119 → 130페이지) 비공개 평가를 8문항으로 늘려 다시 쟀다. 검색 적중·사실 정확·위키만으로 답함 모두 6/8 → 8/8. 새 문항 하나는 공개 위키의 **잘못된 해석**(나중 회의에서 정정된 내용)을 바로잡았는지 묻는다 — 평가가 "새로 배웠나"뿐 아니라 "틀린 것을 고쳤나"까지 본다. 또 평가 답변이 한 분석 수치의 앞뒤 불일치(비율로 역산한 모집단 크기 ≠ 평가셋 크기)를 지적했고, 원본으로 확인할 수 없어 고치지 않고 "확인 필요"만 남겼다. 평가가 위키의 결함 탐지기로도 쓰인다.
- **쌓일수록 예전 문제가 풀린다**: 원인을 확인할 수 없어 "기록 간 차이 · 원인 미확인"으로 남겨 둔 모순 9건 중 1건이, 노션 2차가 들어오자 새 원본에서 근거를 찾아 풀렸다. 모르는 것을 그럴듯하게 지어내 한쪽으로 고치지 않고 남겨 뒀기 때문에 가능했다.
- **글 1편 ≠ 페이지 1개**: 연구 기록 88편이 29페이지로 압축됐다. 원본을 1:1로 옮기면 위키가 아니라 백업이 된다.
- **RAG와 비교** (RAG: 질문할 때마다 외부 문서 조각을 검색해 답변에 붙이는 방식)
  | 항목 | RAG | LLM Wiki |
  |---|---|---|
  | 정리 시점 | 질문할 때마다 검색 | 원본을 넣을 때 한 번 정리(컴파일) |
  | 결과물 | 매번 사라지는 답변 | 남아서 쌓이는 마크다운 페이지 |
  | 모순 처리 | 조각끼리 충돌해도 모름 | 넣을 때 기존 페이지와 대조해 표시 |
  | 사람이 보기 | 벡터DB라 들여다보기 어려움 | Obsidian 그래프·웹사이트로 탐색 |

### 결정과 이유
- **대량 넣기는 single writer(단일 작성자)**
  - 골랐다: 서브에이전트는 `_private/drafts/`에 초안만 쓰고, 병합·목차·로그는 메인 에이전트 혼자 고친다.
  - 왜: 원본 88편을 빨리 처리하려고 서브에이전트를 병렬로 띄웠는데, 여럿이 동시에 같은 페이지를 고치면 서로의 수정을 덮어쓴다.
  - 버렸다: 서브에이전트마다 위키를 직접 고치는 병렬 쓰기. → [[nested-agent]]

## 언제 쓰나 (상황 예시)
- 한 사람이나 작은 팀이 오래 쌓고 직접 읽기도 하는 기록 → LLM Wiki.
- 수만 건이 계속 바뀌는 사내 검색 → RAG.
- 블로그 글이 쌓였는데 "그때 왜 그렇게 정했더라?"를 찾으려면 처음부터 다시 뒤져야 할 때.

## 실습에서 배운 것 / 트러블슈팅
- **모순과 이력을 구분한다.** 두 기록이 다른 말을 하면 덮어쓰지 않고 warning 콜아웃(제목 "모순")으로 두 출처를 남긴다. 반면 부품 교체나 설계 변경처럼 시간이 지나며 바뀐 것은 이력으로 정리한다. 구분하지 않으면 "틀린 기록"과 "바뀐 결정"이 같은 경고로 뒤덮인다.
- **이름을 먼저 고정한다.** 같은 개념이 `mfcc`와 `MFCC-특징`처럼 갈라지지 않도록 병렬 처리 전에 용어집을 승인받는다. 연구 기록 병렬 초안끼리 페이지 이름 불일치 0건.
- 원본 창고는 서로 링크하지 않으므로 그래프에서는 바깥의 흩어진 점으로 보이고, 위키 페이지만 가운데에서 군집을 이룬다.
- **평가 시험지는 원본에서 정답을 뽑는다.** 위키를 보고 문제를 내면 위키에 있는 것만 나와 항상 맞힌다. 처음부터 만점인 문제만 내면 성장도 보이지 않는다. 그래서 회귀 테스트(있던 지식이 유지되는지, 만점이 정상)와 성장 측정(넣기 전 낮고 넣은 후 높음)을 따로 두고, 위키에 없는 질문에는 "없다"고 답해야 정답인 문항도 넣는다. 정답의 핵심 사실은 1~2개로 짧게 잡는다. 정답이 길면 답을 얼마나 길게 썼는지를 재게 된다.
- **대량 압축은 "왜"를 잃기 쉽다.** 원본 여러 편을 한 페이지로 압축하자 "무엇을 결정했나"만 남고 이유가 빠진 곳이 약 30곳 나왔다. 페이지를 하나씩 고치지 않고 규칙서에 "결정은 무엇을 + 왜 + 무엇을 버렸나, 이유가 없으면 (이유 미기록)" 규칙을 넣었다.
- **반영 대상은 "새로 온 것"이 아니라 "처리 안 된 것"으로.** 수집(자동)과 반영(사람이 실행)을 나누자, 자동 수집이 먼저 가져간 글을 반영 명령이 "새 글 0편"으로 보고 놓쳤다. 시스템 간 숫자가 모두 맞아도(정합성) 미처리 원본이 남을 수 있다(완결성). 매번 미처리 원본을 계산하는 상태 기반으로 바꿨다. → [[ai-vault]]
- 구현 사례(설계 원칙, 강제 장치, 트러블슈팅, 운영 판단)는 [[ai-vault]]에 정리했다.
