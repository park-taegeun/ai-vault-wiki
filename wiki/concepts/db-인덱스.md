## 한 줄 정의
키 값과 레코드 위치를 따로 모아 두어, 테이블 전체를 훑지 않고 원하는 행을 빨리 찾게 해 주는 자료구조다. 책의 색인과 같다. 읽기를 빠르게 하는 대신 쓰기 때마다 함께 고쳐야 하는 비용이 든다.

## 핵심 내용
- 조회는 빨라지지만 INSERT·UPDATE·DELETE 때 인덱스도 같이 고쳐야 해서 쓰기가 느려지고 저장공간을 더 쓴다.
- **카디널리티가 높은 컬럼**(서로 다른 값이 많은 컬럼)일수록 효과가 크다. 계좌번호처럼 거의 모든 행이 다른 값인 컬럼이 예다. 값이 몇 종류뿐인 컬럼은 걸러지는 양이 적다.
- **PK를 걸면 UNIQUE 인덱스가 자동으로 생긴다** → [[sql]]
- 만드는 법(DDL): `CREATE INDEX 인덱스이름 ON 테이블이름(컬럼이름);`

### 자료구조
- DB 인덱스는 B-Tree / B+Tree다. 노드 하나에 키를 여러 개 담아 트리 높이를 낮추고, 그만큼 디스크 접근을 줄인다.
- B+Tree는 실제 데이터가 리프에만 있고 리프끼리 연결돼 있어서, 시작점만 찾으면 옆으로 훑으며 범위 검색을 할 수 있다.
- 해시는 평균 O(1)이지만 충돌이 몰리면 O(n)이고 범위 검색(`BETWEEN`, 정렬)에 쓸 수 없다. 균형이 깨진 이진 탐색 트리도 O(n)까지 나빠지므로 AVL·Red-Black 같은 자가균형 트리를 쓴다.

### 레코드 접근 방식 비교
| 방식 | 원리 | 특징 |
|---|---|---|
| 순차 접근 | 저장된 순서대로 처음부터 읽음 | 인덱스가 없을 때의 풀 스캔과 같은 모양 |
| 색인(인덱스) 접근 | 키 값 + 레코드 주소를 색인에 두고, 색인을 찾아 주소로 바로 감 | DB 인덱스가 이 방식 |
| 해싱 접근 | 해시 함수로 키에서 주소를 계산 | 한 건 찾기는 가장 빠르지만 범위 검색 불가 |

### 클러스터형 vs 논클러스터형
| | 클러스터형 | 논클러스터형 |
|---|---|---|
| 저장 | 테이블 자체를 인덱스 순서로 물리 정렬 | 테이블과 별도로 저장 |
| 개수 | 테이블당 1개 | 여러 개 |
| 강점 | 범위 검색 | 여러 조회 조건 대응 |

### 설계에서의 위치
- DB 설계는 요구 분석 → 개념 설계(ER) → 논리 설계(스키마 + 정규화) → **물리 설계(인덱스, 파티션)** → 구현 순서다. 인덱스는 "무엇을 저장할지"가 아니라 "어떻게 빨리 꺼낼지"의 문제라 논리 구조가 정해진 다음에 정한다.
- 3단계 스키마로는 **내부 스키마**(물리 저장 구조) 영역이다. 그래서 인덱스를 바꿔도 개념 스키마·응용 프로그램은 그대로다(물리적 데이터 독립성).
- 같이 외워 두는 DB 객체: 뷰(물리 저장 없는 가상 테이블), 시퀀스(번호 자동 생성), 트리거(조건이 생기면 자동 실행).

### 결정과 이유
- **조회가 많은 컬럼에만 건다**: 쓰기 비용과 저장공간이 늘기 때문이다.
- **정규화가 먼저다**: 반복되는 유사 속성(`전화1`, `전화2`…)마다 인덱스를 만들면 조회는 빨라질 수 있어도 쓰기가 느려진다. 반복 그룹을 행으로 내리는 정규화를 먼저 한다. 성능 모델링 순서는 정규화 → 용량·트랜잭션 유형으로 성능 이슈 확인 → 반정규화 → 성능 검증이고, 인덱스도 같은 맞바꿈(조회↑ 쓰기↓)이라 같은 순서로 판단한다(내 정리).

## 언제 쓰나 (상황 예시)
- WHERE 조건이나 JOIN 조건에 자주 오르는 컬럼이 있고, 그 테이블이 쓰기보다 읽기가 많을 때 → [[sql]]
- 날짜 범위 조회가 많으면 클러스터형이 유리하다.
- 쓰기가 잦은 테이블에 인덱스를 늘리기 전에는 쓰기 비용부터 본다 → [[트랜잭션]]

## 실습에서 배운 것 / 트러블슈팅
- "카디널리티"는 두 뜻으로 쓰인다. 관계형 용어에서 릴레이션의 카디널리티는 **행 수**(차수 = 열 수)이고, 인덱스 이야기에서는 **컬럼의 서로 다른 값 개수**다. 노트에도 두 뜻이 다른 절에 나란히 적혀 있어 섞이기 쉬웠다.
