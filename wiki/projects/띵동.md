## 한 줄 개요
띵동(Ddingdong)은 현관에 붙인 기기가 초인종·노크·화재경보 소리를 ML로 분류해 청각장애인의 스마트폰(카카오톡)으로 알리고, 방문자 사진과 방문자가 한 말의 자막까지 보내는 졸업작품이다. 컨셉은 "기존 알림이 '띵동'으로 끝났다면, 이 시스템은 누가 와서 뭐라고 했는지까지 알려준다"이다.

## 현재 상태
2026-11-19에 시연했고, 다음 날 시연 기록을 정리하면서 개발을 끝냈다(기록 100·101, 2026-11-24 게시). 100은 마지막 개발일지, 101은 시리즈를 닫는 회고다. 기록 97은 96과 본문이 같고, 98은 같은 작업을 더 자세히 적은 글이다. 96~98의 어긋남은 아래 "기록 간 차이"에 모았다.

### 끝난 시점의 상태 (기록 100·101)
- **시연은 관통이지 검증이 아니다.** 08:33~16:12 감지 1,584건: 생활 소음 1,451(91.6%), 노크 71, 초인종 60, 화재 2. 사진 전송 78건. 11시가 347건으로 가장 많았다. 1,584는 감지 수일 뿐이고, 알림 수·차단 수·헛알림 수는 다음 날 기록을 지워 세지 못했다.
- **시연 모델은 5차**다. 보드 확인 조건의 결과를 받지 못한 채 사실상 고른 것이라 확인을 거친 채택이 아니다. 703개 기준 651개(92.6%), 4종 평균 F1 0.8339, 노크 28/47로 노크가 끝까지 가장 약했다 → [[모델-교체-판단]]
- **화재**: 4차 모델 랩실 확인 9/10은 두 번째 감지에 기댄 값이고 첫 감지 기준으로는 6/10이다. 화재 인식이 검증됐다고 말할 수 없다 → [[모델-교체-판단]]
- **미결 16개 중 닫힘 0**, 그중 9개는 "잠정값 그대로 종료"다. 부스 리허설은 열리지 않았다 → [[미결-실재-확인]]
- **사진 응답 대기 2.9초 분기**가 시연 날 처음 한 번 돌았다. 사진이 도착했는지는 확인하지 못했다 → [[kakaotalk-message-api]]
- **펌웨어 2차 알림 상한(부팅당 12번)을 풀었다.** 한 부팅 13번 이상 동작은 직접 확인하지 못했다. 시연 날 사진 전송 51건이 이어지는 동안 기기 연결에 공백이 없었지만 판정이 아니다. 상한은 풀린 그대로 뒀다 → [[fault-injection]]
- **5초 약속**: 고정 시간 최대 약 1.56초(계산값), 정상 망 서버 왕복 8건은 예산의 42~71%, 나쁜 망은 117~149%. 메신저 서버에서 폰까지는 재지 않았다 → [[2단계-알림]]
- **하지 못한 것**: 실제 문, 같은 제품의 옆집 벨, 청각장애인 실사용자 평가. 1인 · 1보드로 진행했다.

### 마지막 개발 구간의 상태 (기록 95~99)
- **기능 동결과 시연 순서 리허설 (기록 99)**: 발표가 가까워져 새 기능을 멈추고 버그 수정·화면 문구·발표 준비만 했다. 예외는 노크 단일 타격 판정 1건이다. 연구실에서 실제 시연 순서(초인종 등록 → 초인종·노크·말소리 → 화재 사이렌형·말소리 겹침 → 차단 2종: 등록 안 한 벨, 사람 없음)대로 리허설을 돌렸고, 합격 기준 없이 관측만 적었다.
- **노크 단일 타격 판정 (기록 99)**: 모델이 노크라고 해도 뚜렷한 타격이 2번 미만이면 알림을 보내지 않는다. 폰을 내려놓는 "툭" 소리에도 모델은 노크를 0.87~0.99로 확신했다. 다음 날 재확인에서 진짜 노크 14번은 전부 발송, 1타·툭 14번은 전부 차단됐다. 한 세션 · 한 사람 · 책상 위 조건이고, 값은 잠정이며, 두 번 두드린 노크는 기준과 같아 여유가 0이다 → [[onset-detection]]
- **사진 카드 중복 수정, 효과는 미확인 (기록 99)**: 사진 전송만 응답 대기 2.9초(잠정)를 따로 두고 응답 대기 시간 초과는 재시도하지 않게 했다. 다음 날 14번 모두 카드가 1장이었지만 그날 시간 초과가 0번이라 새 분기는 한 번도 돌지 않았다 → [[kakaotalk-message-api]]
- **전송 제한 5초 → 2.5초(잠정) (기록 99)**: 서버가 업로드가 끝난 뒤 시각을 찍는 구조는 그대로라 거절이 다시 나지 않는다는 보장은 없다 → [[idempotency-key]]
- **카페 소음 화재 오인 1건 (기록 99)**: 스피커로 튼 카페 소음 영상이 화재경보 0.83으로 분류돼 실제 화재 알림이 나갔다. 화재는 사람 감지를 건너뛰게 설계돼 있다. 대응은 운영 규칙(보드 근처에서 영상·음악 재생 금지)뿐이고 코드는 바꾸지 않았다 → [[out-of-distribution]]
- **실제 장치 시험 1회 (기록 96·98)**: 연구실에서 한 세션, 한 명이 자동 감지 + 시연 기동으로 메신저 실발송까지 이었다. 초인종 2 · 말 없는 노크 1 · 말 있는 노크 1건이 처음부터 끝까지 이어졌다. 이어진다는 확인이지 분류가 잘 맞는다는 검증은 아니다(경우마다 한두 건). 실제 부스 기동을 검증한 것도 아니다.
- **화면 문구는 전부 후보다 (기록 96·98)**: 자막 없음 표시, 보관 기간 지난 사진 안내, 소리 등록 진행 표시, 도움말 6문항, 첫 사용 안내 4단계를 손봤다. 확정 카피는 개발이 끝난 뒤에 정한다. 가짜 데이터 화면 확인은 통과 5 · 미확인 4건이다 → [[화면이-아는-만큼만-말하기]]
- **서비스 모델 (기록 94~99 시점)**: 4차 재학습 후보(인내 15)로 **조건부 교체**를 결정했다. 시연 리허설의 화재 확인(사이렌형·겹침형 포함)에서 하나라도 놓치면 기존 모델로 되돌린다는 조건이었고, 이 조건은 이후 바뀌었다(바뀐 기준 미기록, 4차 유지). 되돌림은 서버 기동 시 모델 경로 하나만 바꾸면 된다. 기록 99 리허설에서 화재(사이렌형·겹침형)를 돌렸지만 판정 기준 없이 관측만 했고 회차와 결과를 짝지은 기록이 분 단위라 일부는 확정할 수 없어, 화재 인식을 검증했다고 말할 수 없다 → [[모델-교체-판단]]
- **분류 클래스는 4종**(초인종 · 노크 · 화재경보 · 기타 소리)이다. 기록 100·101은 네 번째를 "생활 소음"으로 부른다. "기타 소리"는 알림 전 분기에서 막혀서, 알림 문구까지 가는 것은 3종이다 → [[현관-소리-학습-데이터]]
- **자동 감지**(소리가 나면 기기가 스스로 판정)는 집에서 이어지는 것까지만 확인했다. 기준값·창 크기는 잠정이고, 기준 대비 여유(약 1.17배)가 얇은 문제는 미해결이다. 장치 시험에서 헛알림 1건(노크 0.74, 포락선 최대가 진짜 노크의 약 1/8)을 봤지만 관찰 한 건이고 원인도 규명하지 못해 판정 규칙과 모델을 바꾸지 않았다(기록 96·98) → [[onset-detection]]
- **소리 등록 기준 0.20은 잠정**: 연구실에서 같은 벨 거리 0.0778(통과, 기준까지 약 2.6배 여유), 폰으로 튼 다른 벨 0.4008(차단)로 갈렸지만, 같은 벨 거리가 지난번 집(0.016~0.027)보다 컸고 이유는 모른다. 각 n=1이고, 같은 제품의 옆집 벨은 재 본 적이 없다 → [[초인종-유사도-검증]]
  - 중간 발표 시연에서는 등록이 잘 되지 않았다(등록 전 초인종 확신도 0.95 → 0.66). 원인 "벨이 작았다"는 추정이다. 다음 날 소음 영상을 튼 채 차임을 10~20cm, 최대 음량으로 두자 수집 3번 중 3번 성공했다(기록 99).
- **자막이 앞 구절만 오는 증상**: 녹음 길이 가설은 기각됐다. "말 사이 쉼에서 음성 인식이 끝난다"는 가설이 유력하지만 확정은 아니다. 쉼 자리 분할 인식은 합계 효과가 0이라 넣지 않았고, 알려진 한계로 둔 채 시연 대사를 2초 안쪽으로 짧게 유지한다(기록 95) → [[asr]]
- **리셋 버튼 재부팅 시 사람 감지 센서 초기화 실패**: 원인을 아직 모른다. 펌웨어 수정은 정하지 않았고, 운영 우회(USB 재연결 + 첫 알림 카드의 거리 센서 칸 확인)만 있다 → [[vl53l5cx]]
- **센서 멈춤 보호 코드(1초)**: 기준을 1ms로 낮춘 시험 빌드로 경로만 확인했다. 실제 멈춤은 관측하지 못했다 → [[fault-injection]]
- **기기 상태(하트비트) 표시**: 기록 98의 장치 세션에서 기기가 보내는 생존 신호가 서버에 닿아 대시보드가 "연결됨"을 보였다(복귀 1회 관측) → [[화면이-아는-만큼만-말하기]]
  - 세션 중 대시보드가 "현관 기기 꺼짐"을 보인 원인은 기기가 아니라 노트북이 다른 무선 망으로 옮겨 간 것이었다. 폰 핫스팟에 다시 붙이고 그 망의 자동 접속을 끄자 3분 뒤 "연결됨"으로 돌아왔다. 이 한 번으로 기기에 문제가 없다는 것이 증명된 것은 아니다.
- **서버 회귀 테스트 269개**(기록 98, 하루 동안 264→269). 같은 날 화면 렌더 문구 단언은 166→220개, 일부러 깨뜨려 보는 검사는 41→55개로 늘었다. 이 숫자가 화면이 검증됐다는 뜻은 아니다. 라벨 순서 기동 가드, 펌웨어↔서버 대조, 응답 크기 예산, 데모 데이터 계약 테스트가 들어 있다 → [[대조-가드]]
- **시연 리허설**: 기록 99에서 연구실에서 시연 순서대로 한 바퀴 돌렸지만 합격 기준 없이 관측만 했다. 절차 문서의 판정 기준 칸(정할 질문 10개)이 채워졌는지는 글에 없다.

### 기록 간 차이
> [!note] 기록 간 차이 · 원인 미확인
> 서버가 "말 없음"과 "인식 실패"를 구분하는가: 기록 96·97은 서버가 둘을 이미 다르게 취급한다고 함(말 없음은 정상 종료). 기록 98은 서버 코드를 확인해 보니 인식 실패와 빈 결과를 같은 "없음" 값으로 접고 있었다고 함.
> 확인 경로: 띵동 레포 서버의 STT 결과 처리 코드

> [!note] 기록 간 차이 · 원인 미확인
> "사진 보기" 버튼 실측: 기록 96·97은 폰에서 알림 1건을 눌러 이동이 없었다고 함. 기록 98은 시험 발송 6건에서 버튼 자체가 보이지 않았고, 말풍선을 눌러도 이동이 없었다고 함.
> 확인 경로: 다음 실기기 시험에서 재확인

> [!note] 기록 간 차이 · 원인 미확인
> 헛알림 때의 소리와 비교 대상: 기록 96·97은 "아주 약한 소리가 임계를 살짝 넘은 모양"이고 진짜 노크 3건과 비교했다고 함. 기록 98은 소리를 내지 않고 앉아 있었다고 하고, 비교 대상은 봉우리 후보 3개인 진짜 노크라고 함(같은 세션 표의 노크는 2건).
> 확인 경로: 다음 실기기 시험에서 재확인

> [!note] 기록 간 차이 · 원인 미확인
> 시연 날 초인종 건수: 기록 100은 시연 날 초인종 감지가 60건이라고 하고, 같은 글의 등록 기준 재판정에서는 초인종 예측 7건이라고 함 → [[초인종-유사도-검증]]
> 확인 경로: 기록 100 원문, 시연 날 로그

### 닫지 않고 끝난 것
- 노크 단일 타격 판정의 실제 문, 1m 밖, 다른 사람 조건 (값 0.5 · 150ms · 2번은 잠정, 실제 문은 재지 않기로 함) → [[onset-detection]]
- 사진 응답 대기 시간 초과 때 사진 카드가 1장인지 (분기는 1번 돎, 도착 미확인) → [[kakaotalk-message-api]]
- 리허설 문서의 판정 기준 칸과 실발송 예산 (부스 리허설이 열리지 않음)
- 기록 96·97과 98의 어긋남 3건 (위 "기록 간 차이")
- 반올림 갈림 처리 (시연 날 경고 2건은 둘 다 생활 소음, 발송이 갈린 건 0) → [[2단계-알림]]
- 시연장 자동 감지 헛알림 빈도 (기록을 지워 세지 못함) → [[onset-detection]]
- 소리 등록 기준 0.20 확정 (같은 벨 표시가 없어 재판정 못 함) → [[초인종-유사도-검증]]
- 전송 제한 2.5초 (거절 1건, 망 지연 탓인지 가를 기록 없음) → [[idempotency-key]]
- 생활 소음 비율 91.6% ("과하면 다시 본다"의 기준이 없었음)
- 남은 화면 항목(3일 지난 사진, 사진 자동 재시도, 다크 모드, PC 메신저 줄바꿈)과 실제 보드 감지로 본 화면
- 메신저 카드를 PC에서 눌렀을 때의 이동, 실서비스 발송 경로(향후 과제) → [[kakaotalk-message-api]]
- 만료 사진 자동 정리를 다시 볼 조건, 휴지통으로 옮긴 만료 사진 비우기, 센서 데이터선 단서의 표본 → [[i2c]]
- 대시보드 변경(더 보기, 사진 재시도)의 실제 화면 확인, 노트북이 다른 무선 망으로 넘어가지 않게 고정 (기록 100은 노트북 고정 주소와 부스 핫스팟만 적음)
- 원인을 모르는 것: 시연 날 "사진 보내는 중"에서 멈춘 노크 1건, 시작 직후 "현관 기기 꺼짐", 이전 모델의 화재 감지 2건, 센서 초기화 실패, 음성 인식 청구액 0원
- 한 부팅 13번 이상 연속 동작, 5차 모델의 보드 확인 조건(문 모형 노크 10 · 화재 3 · 등록 초인종 3)

## 문제 인식과 타겟
- 국내 청각장애인 등록 인구 441,835명(전체 장애인의 16.8%), 2024년 신규 등록 장애인 중 청각장애 31.7%로 1위다(보건복지부 2024년 등록장애인 현황).
- 2025년 말 기준으로는 449,269명이고 전체 장애인 가운데 두 번째로 많다(보건복지부 2025년도 등록장애인 현황, 보도·전재 기준 수치. 기록 101).
- 청각장애인 26.1%가 1인 가구(약 11만 명)다. 시각 신호표시기 소지율은 0.3%, 보조기기를 사지 않은 이유 1위는 비용 부담(48.2%)이다(2023 장애인 실태조사).
- **핵심 타겟: 5060 중증 청각장애 1인 가구**. 중증 비율 17.7% × 1인 가구 26.1%로 약 2만 명을 추정했다(공식 교차 통계가 없어 비례 할당한 추정치).
- 청각장애인의 95.8%가 50대 이상이고, 50대 장애인 스마트폰 보유율은 97.1%다. 그래서 전용 수신기 없이 앱 알림으로 서비스할 수 있다고 봤다.
- 기존 국내 제품은 모두 "버튼 → LED/멜로디" 구조였다. "현관 부착형 + ML 소리 분류 + 앱 푸시 알림"을 동시에 갖춘 제품이 없다고 판단했다.
- 요구사항(2026-03-27 기획 발표): 24시간 감지, 감지 후 5초 이내 알림, ML 정확도 90% 이상. 이후 [[2단계-알림]]으로 1차 5초 / 2차 15초로 나뉘었다.

## 시연 시나리오 v1
2026-05-09 설계, 2026-05-13 확정. 시연은 "발표"가 아니라 관람객이 돌아다니며 보는 **체험형 부스**다.
- **부스 3영역**: 좌측은 현관문 모형 가벽(인터폰 박스 안에 기기), 가운데는 멜로디가 다른 도어벨 4개·스마트폰·대시보드 노트북, 우측은 차별점과 통계 포스터.
  - 노크면 뒤에 MDF 보강재를 둔다. 폼보드 노크 소리가 학습한 실제 문 노크와 달라 분류가 틀어질 위험 때문이다.
- **진입점 3개** (자유 선택, 머뭇거리는 관람객에게는 ② 추천)
  1. 노크 + 발화: 사람 검증 → 5초 안에 1차 알림, 15초 안에 사진 + 자막 2차 알림.
  2. 초인종 등록 + 분리: 도어벨 하나를 3~5번 눌러 등록하면 다른 도어벨에는 알림이 없다 → [[초인종-유사도-검증]]
  3. 화재경보: 학생이 휴대폰으로 화재경보 음원을 재생한다. 사람 검증을 우회해 즉시 1차 알림 + 화재 대응 수칙을 보낸다.
- 2026-10-15에는 리허설 5단계(등록 → 등록 벨 알림 → 다른 벨 차단 → 사람 없음 차단 → 화재 알림)를 단계마다 1번씩 관통했다.
