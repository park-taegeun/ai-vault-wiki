## 한 줄 정의
카카오 로그인으로 받은 토큰으로 사용자의 카카오톡에 메시지를 보내는 REST API다. [[띵동]]의 알림 채널이다.

## 핵심 내용
- **보내는 방식 두 가지**
  - 친구에게 보내기: 비즈 앱 심사(사업자 등록증 등)가 필요하다.
  - 나에게 보내기(memo): 심사 없이 개인 개발자 계정으로 된다. 받는 사람이 곧 카카오 계정 주인이다.
- **최초 1회 흐름**: 대시보드 접속 → 카카오 로그인 → 동의 화면 → 인가 코드 발급 → 서버가 액세스 토큰 + 리프레시 토큰 발급 → DB 저장.
- **매 알림 흐름**: 액세스 토큰 유효 확인 → 만료면 리프레시 토큰으로 재발급 → 전송 → 로그 기록. 원글 예시 코드는 `https://kapi.kakao.com/v2/api/talk/memo/default/send`에 `template_object`를 POST하고, 401이면 재발급 후 다시 호출한다.

| 토큰 | 유효 기간 | 역할 |
|---|---|---|
| 액세스 토큰 | 6시간 | 실제 API 호출 |
| 리프레시 토큰 | 60일 | 액세스 토큰 만료 시 재발급 |

- `talk_message` scope 동의 방식은 필수 동의 / 선택 동의 / 이용 중 동의 세 가지다.
- **사진은 URL로만 받는다**: 메시지 템플릿은 이미지를 URL로만 받는다. "나에게 보내기"에는 사진 파일을 직접 올리는 기능이 없다.

## 언제 쓰나 (상황 예시)
- 별도 앱 설치 없이 사용자가 이미 쓰는 메신저로 알림을 보내고 싶을 때.
- 알림 받는 사람이 곧 계정 주인인 개인용 서비스.

## 실습에서 배운 것 / 트러블슈팅
- **방식 변경: 친구에게 → 나에게 (2026-04-30, 05-13 확정)**: 처음(2026-04-07)에는 "친구에게 보내기"로 정했고 카카오 로그인을 대시보드 온보딩에 넣었다. 조사해 보니 친구에게 보내기는 비즈 앱 심사가 필요했다. 띵동은 청각장애인 본인이 받는 시스템이라 "나에게 보내기"로 단순화했다. 심사를 피하고, 토큰 관리는 1인분, 동의항목은 1개다. 요구사항(누가 받는가)을 다시 보면 인프라가 줄어든다.
- **scope는 "선택 동의" (2026-05-13)**: 필수 동의는 로그인 흐름이 무거워지고, 이용 중 동의는 전송 때마다 동의 화면이 떠서 데모 흐름에 맞지 않는다. 선택 동의는 OAuth 로그인 때 한 번 묻고 끝이다.
- **토큰 갱신**: refresh_token 자동 갱신은 APScheduler 패턴으로 하기로 했다(2026-05-06). 실제로 저장된 토큰이 만료 상태인데도 발송이 됐고, 그날 첫 요청 시점에 약 9분 전 새로 발급된 흔적이 있었다(기록 58). 오래 안 쓰면 어떻게 되는지는 아직 문서로만 안다.
- **개발자 화면이 바뀌어 있었다 (기록 47)**: 예전 위치를 안내하던 블로그·문서가 모두 틀린 길을 가리켰다. UI를 자주 바꾸는 서비스는 남의 정리보다 지금 화면을 직접 확인하는 게 빠르다.
  - "인증 비밀값이 틀렸다": 예시 자리표시자를 실제 값으로 바꾸지 않고 보낸 실수였다.
  - "인증 코드가 만료됐다": 인증 코드는 몇 분짜리 일회용이다. 받자마자 바로 다음 단계에 이어 붙여 해결했다.
- **왕복 실측**
  - 텍스트 10회(2초 간격): 최소 51.4 / p50 69.2 / p95 84.1 / 최대 93.0ms, 전부 성공. 5초 예산의 1.7%로 병목이 아니었다(기록 47).
  - 사진 URL 포함, 크기 3단계 × 10회(기록 52): 상위 5% 왕복이 ~40KB 488ms, ~97KB 461ms, ~200KB 485ms. 크기가 5배 차이 나도 27ms 이내였다. 카카오는 발송 시점에 사진을 열어보지 않고 URL만 전달하는 것으로 보인다.
- **사진 URL은 우리 서버가 만든다 (기록 50)**: "카카오가 사진 저장까지 해준다"는 처음 계획이 틀렸다는 걸 측정 코드를 짜기 직전에 알았다. 그래서 서버가 사진 공개 URL을 발급하는 구조를 만들었다 → [[2단계-알림]]

> [!warning] 모순
> 기록 20(2026-04-30)은 "카카오 자체 이미지 업로드 API에 multipart로 올리면 카카오 CDN URL이 발급된다, S3 추가 불필요"라며 나에게 보내기 + 이미지 업로드 API를 확정했다. 기록 50(2026-08-01)은 "나에게 보내기는 사진 파일을 직접 올리는 기능 자체가 없고, 우리 서버가 미리 사진을 공개해둬야 한다"며 처음 계획이 틀렸다고 적었다. 이미지 업로드 API가 없었던 것인지, 그 API를 쓰지 않기로 한 것인지 원문으로는 확인되지 않는다. 확인 필요.

- **문서상 본문 길이 제한이 실측과 달랐다 (기록 58)**: 화재 안내문은 소방 자료로 검증한 확정본이라 못 고치는데, 공식 문서상 제한보다 66자 길었다. 원문 그대로 보내 보니 266자가 잘림 없이 도착했다. 확인된 건 "266자가 잘리지 않았다"까지다.
- **사진 카드 본문은 두 줄 (기록 60)**: 자막 15자는 한 줄에 다 보였고, 52자와 110자는 두 줄에서 잘렸다. 둘이 서로 다른 글자 위치에서 잘려서, 기준은 글자 수가 아니라 줄 수이고 위치는 화면 폭에 달렸다. 그래서 사진 카드와 자막을 메시지 두 통으로 나눴다(사진 먼저). 같은 등급의 문서 근거가 하나는 뒤집히고 하나는 맞았다 → [[구현-전-사전-테스트]]
- 데스크톱에서는 단어가 줄 끝에서 어중간하게 잘려 보였지만 휴대폰에선 멀쩡했다. 실제 사용 기기로 확인한다.
- 사진 영역이 안 뜬 원인은 코드가 아니라 시험용 1픽셀 파일이 그림으로 해석되지 않는 조각이었던 것이었다. 입력 자체의 유효성도 확인 대상이다.
- **"토큰 만료" 표시의 진짜 원인은 망 지연 (기록 84)**: 리허설에서 대시보드에 인증 만료 표시가 떴다. 서버 로그의 오류 종류는 만료가 아니라 **갱신 요청 시간 초과**였다.

  | 대상 | 핫스팟 재시작 전 | 재시작 후 |
  |---|---|---|
  | 메신저 인증 서버 | 8.43초 | 0.23초 |
  | 메신저 API | 6.75초 | 0.35초 |
  | 음성 인식 서비스 | 4.29초 | 0.25초 |

  - "첫 발송 때 자동 갱신되니 걱정 없다"는 안내는 망이 정상일 때만 참이었다. 대시보드가 갱신 실패를 전부 같은 표시로 보여 줘서 망 지연과 진짜 만료가 구분되지 않았다 → [[화면이-아는-만큼만-말하기]]
  - 리허설 전 절차에 추가: 외부 서버 응답 속도부터 재기, 테스트 발송 1건으로 갱신을 미리 끝내 두기.
- **사진 카드가 두 장 도착 (기록 84, 미해결)**: 첫 요청이 실제로는 도착했는데 시간 초과로 처리돼 재시도가 한 장 더 보낸 것으로 추정한다(로그 순서 기반). 기록 86의 실제 연결 관통 1회에서는 중복이 없었지만, 원인을 푼 게 아니라 이번 한 번 안 나타난 것이다 → [[idempotency-key]]
